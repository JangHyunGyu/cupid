# Character image assets

All three applications use the same source layout and registry. Source images live only under `assets/characters`; previous public filenames are compatibility aliases generated by the build, not additional editable source files.

```
assets/characters/<character-id>/avatar/01/portrait.webp
assets/characters/<character-id>/avatar/01/portrait.png
assets/characters/<character-id>/avatar/01/thumb.webp
assets/characters/<character-id>/expressions/smile/01/sprite.webp
assets/characters/<character-id>/expressions/smile/01/chat.webp
assets/characters/<character-id>/expressions/smile/02/sprite.webp
```

Use stable IDs, lowercase filenames, and two-digit variant numbers. `sprite` is the full portrait, `chat` the chat crop, `portrait` the profile avatar, and `thumb` the card thumbnail. WebP and original fallback files share the same stem. Do not renumber existing variants. A second variant is a separate asset, not a replacement of `01`; registering it does not automatically change expression selection.

Members use `<parent-id>/members/<member-id>` as the owner. Outfit-specific images use `<owner>/outfits/<outfit-id>/expressions/<expression>/<variant>/...`. Historical unassigned owners use `legacy/<old-owner>`. Imported historical avatar alternatives may have a `legacy-...` variant; use numeric variants for new additions.

`config/character-assets.json` records owner, expression, variant, source path, public aliases, byte size and SHA-256. Add files using the layout above, then run:

```
npm run characters:sync
npm run characters:check
npm run cache:check
npm run build
```

Update the application's character configuration to select newly registered images. `characters:sync` registers files and updates checksums; it never generates images or rewrites character behavior. Remove a source and its registry entry together only after checking runtime references and historical compatibility. `characters:list` prints the inventory.

Serve `dist/` for local static previews. Do not serve the repository root as the production site. Builds convert literal historical URLs to canonical URLs. Harem and Chatbot also emit legacy URLs for saved conversations and dynamic older clients. The registry is a build input, not an eager browser download list. Existing lazy loading and WebP fallback behavior remain in place.

Cupid images remain private. Its build excludes source character images; `media-gate` and the media API map canonical paths to existing logical asset IDs, grants and R2 keys. Existing `characters/seyoun_*` IDs retain their spelling even though the canonical owner is `seoyeon`. Direct canonical and legacy sprite URLs are denied. Use the existing private-media upload workflow for new encrypted assets; moving files does not require reuploading existing objects. A plain static server cannot reproduce Cupid's media authorization: use the existing E2E fixture or Pages Functions for previews.

Cloudflare Pages must build with `npm run build` and publish `dist` in all three projects. Run cache checks, asset tests and project-specific validation before publishing.
